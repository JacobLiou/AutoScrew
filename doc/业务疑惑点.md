业务方这句话本质是在补一条**物料工艺主数据**，而你们现在系统里「螺钉」其实被拆成了好几层、含义还不完全对齐。先把概念拆开，再谈关联怎么建，会比较稳。

## 1. 先分清「螺钉」指什么

现场口语里的「螺钉」至少有 4 种，混在一起会把模板库做糊：

| 概念 | 业务语义 | 现有落点 |
|------|----------|----------|
| **螺钉料号** `part_no` | 物料身份（M2×6 黑锌等） | marker 可选 `partNo`；`ScrewRecipeDto.PartNo` |
| **规格外观** | 画板圈大小、吸头选型提示 | `ScrewTypeCatalog`（M1.0–M4，偏 UI） |
| **锁附工艺** | 扭矩/角度/分段/判定 | `ScrewRecipeDto` 目标扭矩区间；更完整的是 `TighteningParameterTemplate` |
| **设备参数槽** | 电批里可写的 ParameterId（容量有限） | `ControllerParameterId`（设备 1–500） |

PRD 说「一个螺钉对应一种锁附参数」，更贴近：

> **螺钉料号（或工艺螺钉定义）→ 一套标准锁附参数**

而不是「产品上每一个打点位各自发明一套参数」。位号只是**引用**这套参数，外加位置/顺序/供料通道等作业信息。

## 2. 业务真正想要的关系（建议模型）

可以看成三层，而不是「一个大模板包塞所有东西」：

```text
[A 工艺模板库 / 大而全]
  ScrewSpec（螺钉定义）
    - partNo / 名称 / 规格
    - 默认吸头、供料通道建议
    - tighteningRecipeId  → 指向锁附参数模板
    - （可选）判定规则、返修参数

[B 设备配置 / 受限子集]
  DeviceSlot[1..N]
    - 从 A 拉取并写入的 ParameterId
    - 槽位数量、当前激活集受硬件限制

[C 产品模板 / 布局 + 引用]
  ProductTemplate(PN)
    - surfaces / markers（坐标、顺序）
    - marker.partNo 或 marker.screwSpecId  → 引用 A
    - 作业时再解析成 ControllerParameterId（来自 B 的映射）
```

对应 PRD 221–231 的两句话：

- 「模板库大而全」→ **A**
- 「设备配置是子集合」→ **B**（从 A 勾选/下发到本机电批槽位）
- 「拉一下就配置到设备」→ **A → B 的发布动作**，不是把整个产品图下到电批

产品模板（你们已有的 `product-template.json`）更适合继续管**布局与引导**，不宜变成「全公司唯一参数库」。

## 3. 和现状的差距（为什么业务现在才提）

当前链路大致是：

- 产品模板：位图 + `screwTypeId`（规格圈）+ 可选 `partNo`
- Recipe：按**位号**带扭矩窗口和可选 `ControllerParameterId`
- 拧紧参数页：本地 preset / 设备槽，偏**设备工程师配置**，尚未与「螺钉料号主数据」强绑定

也就是说：

1. `ScrewTypeCatalog` ≠ 工艺螺钉库（只是画板尺寸）
2. 参数库与料号是**松散或按位号**关联，不是「选螺钉就带出参数」
3. 「大库 → 设备子集」这条发布路径还没产品化（有本地 preset、有读写下发，但缺「螺钉维度的目录与选用」）

业务用过之后会自然要求：**建产品时选螺钉料号，参数自动带出；换产时把本工位需要的那几套参数灌进电批。**

## 4. 关联设计上必须拍板的几个点

**（1）主键用什么？**  
- 仅 `partNo`：MES/物料体系清晰时最好  
- `partNo + 工艺版本`：同一料号不同扭矩/分段（客诉改工艺很常见）  
- 还是内部 `screwSpecId`，`partNo` 只做显示与追溯  

**（2）一对一是否绝对？**  
PRD 写「一种锁附参数」。实务里常要：

- 标准拧紧 vs 返修拧紧（你们已有 REWORK 概念）
- 不同工位/电批型号下的兼容参数变体  

建议对外仍说「一颗螺钉一种标准工艺」，对内允许：

`ScrewSpec → { standardRecipe, reworkRecipe?, deviceProfile? }`

**（3）产品位号能否覆盖参数？**  
两种策略：

- **严格引用**：位上只挂 `partNo`，参数一律来自库（防错强，适合量产）  
- **引用 + 例外覆盖**：个别位可改扭矩（灵活，易漂移）  

按你们防错目标，默认应 **严格引用**；覆盖需技术员权限 + 留痕。

**（4）设备子集怎么选？**  
一个产品用到 3 种螺钉 → 本机只需 3 个参数槽。要明确：

- 槽位是**按工位常驻缓存**（多 PN 共用，槽满则替换）  
- 还是**换产时整包刷新**（当前 PN 用到的集合）  

「拉一下就配置」更像后者，运维成本更低。

**（5）和 MES 谁是权威？**  
- 库在上位机本地 / UNC：α 快，多机一致性靠同步  
- 库在 MES/工艺系统：权威清晰，上位机只缓存与下发  

你们 V1.2 已有产品模板 MES 同步；螺钉参数库可以走同一套「目录 + 包 + hash」，但实体应独立于 PN 产品包。

## 5. 推荐业务表述（方便回写 PRD）

可把 3.2.4 收敛成一句话：

> **螺钉工艺模板库**维护「料号 → 锁附参数（及供料/吸头建议）」；**设备参数区**只缓存本工位启用的子集并写入电批槽位；**产品模板**只描述布局与每位引用的料号。扫码换产后，按产品用到的料号集合一键下发到设备。

作业解析链：

```text
SN → PN → 产品模板(markers.partNo)
       → 查螺钉库得到 TighteningRecipe
       → 查本机槽位映射得到 ControllerParameterId
       → 供料 + 拧紧
```

这样既满足「一个螺钉一种参数」，又保住「设备参数受限」和「拉一下就配好」。

## 6. 建议你跟业务确认的短清单

1. 「螺钉」主键是物料料号，还是内部工艺码？同一料号会不会有多套工艺版本？  
2. 返修是否共用同一套，还是强制第二套参数？  
3. 产品模板打点时：只能从库选螺钉，还是允许手填扭矩？  
4. 换产下发：只写当前 PN 用到的参数，还是维护工位长期参数池？  
5. 参数变更后：已下发设备是否强制失效/提示重拉？历史 SN 追溯用当时快照还是最新库？
